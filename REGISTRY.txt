      acceptable; if sync starts failing under concurrent writes, memoise the

      HELPER CALDAVSYNCWORKER AUDIT
      ───────────────────────────────────────────────────────────────────────────────
      [x] AUDITED  CalDAVSyncWorker/doWork creates one CalDAVSyncEngine per run.
            Engine fetches accounts from DB and calls syncAccount(account).
            CalDAVSyncWorker.syncNow() enqueues unique one-time work; schedule*()
            uses KEEP/REPLACE policies. No instance pile-up on the WorkManager side.

      [x] AUDITED  CalDAVSyncEngine.syncAccount is reused per call and does NOT hold
            state between accounts. It builds a CalDAVClientFactory.create() client
            inside the method, uses it for that account, then drops it. OkHttpClient
            is pooled by factory; auth interceptor cost is tiny.

      [x] CALDAV-CLIENT-REUSE
            Added per-(serverUrl,username) client cache in CalDAVClientFactory.
            Factory.create() now reuses cached CalDAVClient instances; evict()
            and clearCache() provided for password rotation. AccountRepository.save()
            evicts on password change. Sync worker and repositories automatically
            benefit from reuse. Memory footprint: one client per unique account
            credentials per process. Low risk; functional improvement.

      [x] REMINDERWORKER  Lightweight; no CalDAV client use. Just NotificationHelper.
          No shared-state issue.

      VIEWMODEL / UI REVIEW FINDINGS
      ───────────────────────────────────────────────────────────────────────────────
      [ ] EVENT-EDIT-DIALOG-STATE
            EventEditDialog computes initStart/initEnd from preselectedDate at
            composition time. selectedDate in CalendarViewModel updates when the
            user taps a day, but if the dialog is opened from a non-day source
            it still confirms preselectedDate correctly. No bug found, but the
            dialog does not react to further selectedDate changes while open.
            Acceptable for launch; revisit if we add live preview.

      [x] CALENDAR-TOPCONTROLS  CalendarTopBar uses fixed "Mo/Wk/Dy/Ag".
          ViewMode state is a plain String instead of enum; safe but weak-typed.
          Recommendation: rename to enum class ViewMode for compile-time safety.
          No functional defect.

      [x] MONTHVIEW-REGROUP   MonthView groupBy is already keyed by LocalDate
          using ZoneId.systemDefault(). This matches how DayView/WeekView select
          events; behaviour is consistent.

      [ ] WEATHER-DEBOUNCE    Weather fetch is debounced at 500ms. If the user
            mashes prev/next quickly, this may produce a burst of fetch calls
            then discard them. Fine for MVP; later move debounce before collect.

      [ ] PERSONFILTER-PER-SCREEN
            Each screen exposes its own selectedPersonFilter flow. There is no
            global people filter. This is fine for single-view filtering.

      [ ] WEEKVIEW-DAY-COLUMNS   Day columns repeat Instant.ofEpochMilli(...)
            conversion for each event. With few events the cost is negligible.
            For aggregation, consider extracting a single map<date, list> similar
            to MonthView.

      [ ] DAYVIEW-HOUR-GUTTER  Uses 23x 60.dp divisions. Same chrome concern as
            WeekView; only a wall-mode specific concern.

      [ ] AGENDAVIEW-HUMAN-LABELS  Uses nicely formatted Today/Tomorrow/date.
          Good; no change needed.

      REPOSITORY SYNC CORRECTNESS OBSERVATIONS
      ───────────────────────────────────────────────────────────────────────────────
      [ ] CALENDAR-SAVE-CLIENT   CalendarRepository.saveEvent creates a new
            CalDAVClient for each remote event. Concurrency handling is via
            withContext(Dispatchers.IO) only; no job limit in the factory.
            Acceptable at family-tablet scale; flag for later if accounts grow.

      [ ] TASK-COMPLETED-PUSH   TaskRepository.setCompleted pushes each task
            completion immediately. Could double-sync if multiple tasks
            complete in same second. No dedup; backoff in worker might race.
            Low risk at small scale; add batching during Rewards/Chores depth.
